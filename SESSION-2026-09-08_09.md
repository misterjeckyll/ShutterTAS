# Sessions des 8 et 9 septembre 2026 — ShutterTAS

Compte rendu technique de deux matinées de travail sur le mod UE4SS de *Shutter*.
Destiné à quelqu'un qui reprend le projet : ce qu'on a appris sur le jeu, ce
qu'on a construit, ce qui reste cassé, et pourquoi.

**Build de référence : `2026-09-09-16`.**

---

## 1. Point de départ

Le mod affichait un HUD de debug en jeu (compteur de frames, inputs) et
plantait au lancement avec :

```
main.lua:498: bad argument #2 to 'format' (number expected, got UObject)
```

`root.RelativeLocation` ne renvoyait pas un `FVector` exploitable selon le
contexte. Corrigé en passant par les accesseurs Blueprint, avec une cascade de
stratégies dont on loggue celle qui a fonctionné. En pratique c'est
`root:K2_GetComponentLocation()` qui répond sur ce build.

## 2. Ce qu'on a appris sur *Shutter*

Le `.pak` décompilé se trouve dans
`Shutter/Content/Paks/Shutter-WindowsNoEditor/`. Ce sont des `.uasset`/`.uexp`
bruts, mais la table de noms est lisible en clair (`strings -n 4`), ce qui
suffit à retrouver propriétés et fonctions sans outil dédié.

### Keith est un personnage ALS v4

`Keith_BP` est bâti sur **Advanced Locomotion System v4**. C'est le fait le
plus structurant du projet : l'état du joueur n'est pas « position + rotation »,
c'est une machine à états.

```
MovementState  MovementAction  Stance  Gait  DesiredGait  AllowedGait
RotationMode   ViewMode        OverlayState
AimingRotation TargetRotation  InAirRotation  LastVelocityRotation
InAirTimer     JumpCounter     MantleType     RagdollPose
Speed          MovementInputAmount  Acceleration
```

Un LOAD qui ne restaure que la position téléportera Keith mais le laissera dans
le mauvais état de locomotion — non déterministe, donc inutilisable pour un TAS.

Valeurs des enums, extraites des `UserDefinedEnum` du pak
(`Content/Characters/AdvancedLocomotionV4/Data/Enums/`) :

| Enum | Valeurs (dans l'ordre) |
|---|---|
| `ALS_MovementState` | None, Grounded, InAir, Ragdoll, Mantling |
| `ALS_MovementAction` | None, LowMantle, HighMantle, Rolling, GettingUp |
| `ALS_Stance` | Standing, Crouching |
| `ALS_Gait` | Walking, Running, Sprinting |
| `ALS_RotationMode` | VelocityDirection, LookingDirection, Aiming |
| `ALS_ViewMode` | ThirdPerson, FirstPerson |
| `ALS_OverlayState` | Default, **Polaroid**, **Picture**, **Covered** |

`OverlayState` est spécifique à Shutter — c'est l'état de l'appareil photo.

**Attention aux faux amis.** La table de noms contient aussi des variables
locales de fonctions. `ActualGait` y figure mais n'est pas un membre lisible :
`pawn.ActualGait` renvoie un userdata. Le bon nom est `Gait`. Toujours vérifier
en jeu, pas seulement dans le pak.

### La mécanique photo — objets bleus stockés puis reposés

Photographier un objet bleu le stocke ; on peut le reposer plus tard, à une
échelle réglable. Ce qui est lisible côté mod, **mesuré en jeu** :

| Propriété de `Keith_BP_C` | Type |
|---|---|
| `PictureInventory` | struct `SavedPicture` — le contenu du slot |
| `PictureTaken`, `PictureLoaded`, `CameraAvailable` | booléens |
| `LastObjectHitDistance`, `ObjectScaleRate` | nombres |
| `PictureMesh`, `PictureMaterial` | composant et matériau de la photo tenue |

La struct `SavedPicture`
(`Content/Characters/Keith/Data/SavedPicture`) contient :

```
SlotUsed (bool)   MeshType (enum ShutterMeshTypes)   NumberCode (int)
OriginalDistance  OriginalRotation   Original_Scale
ShutterMeshPivotRot   MinSize   MaxSize
```

`ShutterMeshTypes` : `SimulatedMesh`, `Door`, `StaticMesh`, `Anomaly`.

**L'identité de l'objet capturé est dans `ObjectClass`** — une `ClassProperty`
de type `Actor`, à l'index 3 de la struct. C'est ce que le jeu respawne quand
on repose l'objet ; son `GetFullName()` donne la classe réelle
(`SM_Cube_BP_C`…). Je l'avais d'abord ratée parce que mon extraction de la
struct s'était arrêtée aux premiers noms trouvés : les index relevés étaient
6, 9, 12, 16, 19, 23, 29, 31, 34 — visiblement troués, ce qui aurait dû
m'alerter tout de suite.

**Ce qui n'est PAS lisible, et pourquoi :**

- **le mesh de l'objet** — `PictureMesh` est le plan de la *photo tenue en
  main*, toujours le même quel que soit l'objet ; celui-ci n'apparaît que via
  `PictureMaterial`, un matériau dynamique ;
- **l'échelle courante** — `BlueItemScale` et `DesiredScale` sont des locales
  de fonctions. Seule `Original_Scale` (l'échelle à la capture) est dans la
  struct ; `MinSize`/`MaxSize` donnent la fourchette de réglage autorisée, et
  varient d'un objet à l'autre ;
- **`PictureTaken` / `PictureLoaded`** — drapeaux transitoires d'animation,
  invisibles à 7 Hz. `SlotUsed` est le seul état stable.

**Deux pièges mesurés, pas supposés :**

1. **Les membres d'une `UserDefinedStruct` ne répondent qu'à leur nom manglé.**
   `inventory.SlotUsed` rend `nil` ; `inventory["SlotUsed_16_DE00E4E54FAA1A4F35336E86899D8FDA"]`
   rend `true`. Le compilateur Blueprint suffixe chaque membre d'un index et
   d'un GUID, tous deux lisibles dans le `.uasset` de la struct.
2. **`TrivialObject` veut dire « propriété absente ».** Vérifié avec un témoin :
   lire un nom volontairement inexistant renvoie exactement le même
   `TrivialObject` que `ObjectInRange`, `BlueItemScale`, `ClosestObject`,
   `HasRoom` ou `ObjectType`. Ces noms figurent dans le pak mais sont des
   variables **locales de fonctions**, pas des membres — comme `ActualGait`.
   Aucun accesseur (`:get()`, `:Get()`, `:GetValue()`, `:Value()`,
   `:ToString()`, `:GetFullName()`) ne les déballe, parce qu'il n'y a rien
   dedans.

### Mécanique de gravité custom

`JumpGravity`, `JumpZVelocity`, `JumpGravity_Gravity_*` côté Keith, et
`GravitySolved` dans la sauvegarde. Probablement central pour le routing.

### La sauvegarde du jeu est inutilisable pour un TAS

`Blueprints/SaveGame/ShutterSaveGame` ne contient que :

```
CurrentCheckpoint  CheckpointsUnlocked  UnlockedFloors  TutorialComplete
CollectedCassettes CollectedDocuments   GravitySolved
CurrentHat CurrentSkin HatsUnlocked SkinsUnlocked KeithHats KeithSkins
```

Aucune position, aucune vélocité, aucun état de mouvement. C'est du checkpoint,
pas de l'état-frame — il faut construire notre propre snapshot.

En revanche `Shutter_PlayerController` sait manipuler ces slots
(`CreateSaveGameObject`, `DoesSaveGameExist`, `SaveGameToSlot`,
`LoadGameFromSlot`), utile pour poser un état de progression connu avant un run.

### Fonctions d'input

Le scan F9 (voir §4) liste 43 fonctions d'événement d'input. Les utiles :

```
Keith_BP_C:InpActEvt_RunAction_K2Node_InputActionEvent_0   et _1   (Pressed/Released)
Keith_BP_C:InpActEvt_JumpAction_..._8 et _9
Keith_BP_C:InpActEvt_ObjectScaleMode_..._2 et _3
Keith_BP_C:InpActEvt_Aim_..._4 / Shoot_..._5 / Interact_..._7 / Cancel_..._6
Keith_BP_C:InpAxisEvt_LookUp/Down_..._2  et  LookLeft/Right_..._3
Shutter_PlayerController_C:InpAxisEvt_MoveForward/Backwards_..._0  et  MoveRight/Left_..._1
```

**Découverte importante, mesurée :** les hooks posés sur
`Shutter_PlayerController_C` se déclenchent (53 660 appels en ~7 min, soit
2 axes × 60 fps). Ceux posés sur `Keith_BP_C` ne se déclenchent **jamais**
(0 appel). `InpActEvt_AnyKey` sur le PlayerController ne se déclenche pas non
plus. Autrement dit : sur cette classe, les événements d'**axe** passent, les
événements d'**action** non. La raison n'est pas élucidée.

## 3. Le HUD aujourd'hui

Dix lignes, rafraîchies à ~7 Hz (`HUD_REFRESH_INTERVAL = 8`) :

```
F 00005587                                    compteur de frames TAS
T 00:12:04.318                                temps de jeu (rafraîchi à ~2 Hz)
I F 1.00 | R 0.00                             axes de déplacement
E (keybinds off)                              inputs — désactivés, voir §5
S Grounded | None | Standing | Polaroid       MovementState|Action|Stance|Overlay
G Walking>Running | Aiming | Spd 0.0 | In 0.00
P X -844.93 | Y -3525.00 | Z 282.43           position monde
R Yaw 90.00 | Cam P/Y 353.96/81.56            rotation acteur + caméra
V X 0.00 | Y 0.00 | Z 0.00                    vélocité
C SM_Cube_BP_C (SimulatedMesh) | Ech 0.35 | Rot 0/90/0 | Bornes 0.10-0.50 | Dist 50 | Code 10
```

La ligne `T` a été débloquée le 09/09 : `GetTimeSeconds` n'est pas une
propriété du pawn (la lire rendait un `TrivialObject`, donc « absente »), c'est
une `UFunction` **statique** qu'on appelle sur l'objet par défaut de
`GameplayStatics`, avec le pawn comme contexte de monde. Même correction de
méthode que pour la position avec `K2_GetComponentLocation`.

- **F7** bascule l'affichage
- **F8** dump de diagnostic (état interne, compteurs d'événements)
- **F9** scan des fonctions d'input du jeu
- **F1** sonde des propriétés du pawn (types réels, témoin, dump de la struct)

`TAS_CONFIG`, en tête de `main.lua`, permet de désactiver chaque ligne et chaque
famille de hooks indépendamment — c'est l'outil de bisection quand quelque
chose casse.

### Limite connue : la ligne `E` ne mesure pas l'état des touches

`RegisterKeyBind` de UE4SS **ne notifie que la pression**. Il n'émet aucun
événement de relâchement, et ne répète rien pendant le maintien. On ne peut
donc savoir ni qu'une touche est encore enfoncée, ni qu'elle vient d'être
lâchée.

La ligne `E` affiche en conséquence *les touches pressées dans la dernière
demi-seconde*, plus la dernière connue en repli pour éviter une ligne vide.
Concrètement :

```
appui sur Z (maintenu)      → E Z
appui sur Q sans lâcher Z   → E Z Q      puis  E Q   (Z expire au bout de 0,5 s)
relâchement de Q            → E Q        (aucun événement, Q reste affiché)
```

Ce n'est pas un bug d'affichage : l'information n'existe pas côté mod.

**Exception, et elle compte :** les événements d'**axe** se déclenchent à chaque
frame avec leur valeur courante. L'état des touches de déplacement est donc
réellement mesuré, en continu, sur la ligne `I` — et c'est vérifié
(53 660 appels en 7 minutes). De même, l'état maintenu du sprint et de
l'accroupissement se lit sur le pawn (`DesiredGait`, `Stance`), lignes `S` et `G`.

**Conséquence pour un TAS :** la ligne `E` est un confort de debug, pas une
source d'enregistrement. Un journal d'inputs rejouable devra être bâti sur les
événements d'axe et sur l'état du pawn, jamais sur les keybinds.

### Sous-cas : la touche Shift

**Shift, Ctrl et Alt ne peuvent pas être affichés seuls**, et pour une raison
supplémentaire : la table `Key` de UE4SS ne les contient pas du tout. Ils
n'existent que comme `ModifierKey`. Il n'y a donc rien à enregistrer, et aucun
événement n'est émis quand on les presse seuls.

Contournement en place : chaque touche est enregistrée quatre fois — sans
modificateur, puis avec Shift, Ctrl et Alt (629 keybinds). Shift apparaît donc
dès qu'une autre touche est pressée en le maintenant (`SHIFT+Z`), mais jamais
seul.

Les deux autres voies ont été essayées et sont fermées : les événements
d'action Blueprint ne se déclenchent pas, `AnyKey` non plus.

## 4. Outillage créé

| Fichier | Rôle |
|---|---|
| `deploy.sh` | Synchronise `Scripts/` vers le dossier Proton du jeu |
| `triage.sh` | Symbolise le dernier crash avec `UE4SS.pdb` |
| `check_order.py` | Détecte les appels à une fonction inexistante ou définie plus bas |
| `mdmp.py` | Décode l'enregistrement d'exception des dumps UE4SS |

### `deploy.sh`

Le jeu tourne sous Proton ; le chemin Windows vu par UE4SS
(`S:\steamapps\...`) correspond côté Linux à
`~/.steam/steam/steamapps/common/Shutter/Shutter/Binaries/Win64/Mods/ShutterTASDiscovery/Scripts/`.

```bash
./deploy.sh            # copie et vérifie
./deploy.sh --bump     # incrémente TAS_BUILD puis copie
./deploy.sh --check    # compare sans écrire
```

Il refuse de déployer si `luac -p` échoue ou si `check_order.py` trouve un
problème, sauvegarde l'ancien fichier et vérifie la copie octet par octet.

**`TAS_BUILD` est loggué au chargement.** Ça paraît trivial, mais on a perdu une
heure sur un fichier périmé côté jeu : le symptôme ressemblait à un bug de code.
Toujours vérifier le numéro de build avant de conclure quoi que ce soit.

### `triage.sh` — symboliser les crashs

`UE4SS.pdb` (124 Mo) est livré avec UE4SS. Avec `llvm-symbolizer`
(`pacman -S llvm`), on obtient le nom exact de la fonction qui plante au lieu
d'un offset.

```bash
./triage.sh          # dernier crash
./triage.sh -n 3     # les 3 derniers
```

Les crashs atterrissent à **deux endroits** selon qui les attrape :

- `.../compatdata/2314110/pfx/.../Shutter/Saved/Crashes/UE4CC-*/` — dumps
  Unreal, avec `CrashContext.runtime-xml` et une pile portable ;
- `Binaries/Win64/crash_*.dmp` — dumps UE4SS, **sans** pile portable.

`triage.sh` gère les deux : pour les seconds il appelle `mdmp.py`, qui décode
l'enregistrement d'exception du minidump (adresse fautive, type d'accès, module)
et rend l'adresse à symboliser. Base de `UE4SS.dll` : `0x180000000`.

### `check_order.py`

En Lua, une référence à un `local` défini plus bas se résout sur un **global**,
donc `nil`. `luac -p` ne le voit pas, l'erreur n'apparaît qu'à l'exécution.
Ce piège nous a eus trois fois ; le contrôle est maintenant dans `deploy.sh`.
Il a aussi révélé un bug préexistant dans `inspect_hud.lua` (`is_valid` appelée
ligne 56, définie ligne 111) qui rendait ce script inopérant.

Correctif type : `local nom` en tête, puis `function nom()` plus bas.

**Seconde règle, ajoutée le 09/09 :** il signale aussi les appels à une
fonction **snake_case définie nulle part**. Nos helpers sont en snake_case,
l'API UE4SS en PascalCase, donc la distinction est fiable. Le contrôle ignore
le contenu des chaînes, sinon `"%s (%s)"` passerait pour un appel à `s()`.

Ce qui l'a motivé : en réécrivant la ligne `C`, j'ai supprimé le helper
`describe()` sans retirer ses appels. La branche concernée n'était atteinte que
lorsqu'un objet était stocké — elle a produit **433 erreurs** en une minute,
et UE4SS a fini par planter dans `luaL_traceback`, c'est-à-dire en fabriquant
le message de ces erreurs.

## 5. Les crashs — ce qu'il faut savoir

Huit signatures distinctes en une matinée. Cinq à la frontière Lua↔UE4SS,
trois dans le moteur Lua lui-même — et ces trois-là ont fini par s'expliquer
par une seule cause, voir « corruption du tas Lua » plus bas :

| Fonction UE4SS qui plante | Ce qu'on faisait |
|---|---|
| `FText::construct` | créer un `FText` pour un `SetText` |
| `UFunction::construct` | résoudre une méthode sur un `UObject` |
| `call_ufunction_from_lua` | appeler une `UFunction` sur un objet non validé |
| `lua_getiuservalue` | lire une propriété (`pawn.Champ`) |
| `AActor::construct` | `FindFirstOf()` construisant un wrapper d'acteur |
| `luaH_next` | itérer une table Lua *(bug de notre côté)* |
| `getgeneric` | lire une table Lua corrompue *(bug de notre côté)* |
| `luaH_set` (via `convert_struct_to_lua_table`) | UE4SS écrivant une struct dans une table Lua |

### Trois règles qui en découlent

**1. `pcall` ne protège de rien ici.** Un access violation en C++ tue le
processus avant que Lua ne voie quoi que ce soit. `pcall` n'attrape que les
erreurs Lua. Les cinq premières signatures sont toutes survenues *à l'intérieur*
d'un `pcall`.

**2. `IsValid()` est nécessaire mais pas suffisant.** Un test `if not obj then`
laisse passer un objet détruit : au changement de niveau, les références Lua
restent non-nil mais pointent sur de la mémoire libérée. Il faut `obj:IsValid()`
avant tout accès. Mais valider ne suffit pas — `overlay_alive()` appelait
`IsValid` 11 fois par frame et était devenu, à lui seul, la première cause de
crash. **Valider coûte un appel, donc valider trop plante aussi.**

**3. Le volume est le vrai levier** — pour les cinq signatures côté UE4SS. Chaque correctif durable a consisté à faire
*moins* d'appels, pas à mieux les protéger :

- `set_text()` ne réécrit un widget que si le texte a changé — à l'arrêt, on
  passe de 9 écritures par rafraîchissement à une seule ;
- le rafraîchissement est à ~7 Hz, pas 60 ;
- le contrôleur est mis en cache, `FindFirstOf` n'est plus appelé en boucle ;
- les callbacks de touches et de hooks sont **purement Lua** : ils posent un
  drapeau, le tick fait le rendu.

Bilan : de plusieurs centaines de traversées Lua↔C++ par seconde à moins de 30.

### La corruption du tas Lua — le diagnostic central

Trois symptômes en apparence sans rapport se sont révélés être une seule et
même maladie :

```
main.lua:766: bad argument #1 to 'sort' (table expected, got string)
        ... alors que `active` est une table locale créée 15 lignes plus haut

getgeneric   ltable.c:302   lecture de 0x687461BE
        ... une adresse dont les octets sont de l'ASCII : « h », « t », « a »

luaH_set     ltable.c:840   lecture de 0xffffffffffffffff
        ... pile : call_ufunction_from_lua → push_structproperty
                   → convert_struct_to_lua_table → aux_rawset → luaH_set
```

Le dernier est le plus parlant : UE4SS plante en **écrivant** dans une table
Lua qu'il vient de créer pour y convertir une struct renvoyée par une
`UFunction`. Autrement dit, **le tas Lua lui-même est corrompu**.

Ça explique l'erreur de tri, qui était statiquement impossible : le marqueur
de type de la variable avait été écrasé en mémoire. Ce n'était pas un bug de
logique — chercher la faute dans le code Lua était une impasse.

**Leçon de méthode :** face à un message d'erreur qui ne peut pas se produire
d'après le code, suspecter la mémoire avant de suspecter sa propre logique.
Ici, une heure aurait été perdue à relire une fonction parfaitement correcte.

Deux pistes, non départagées à la fin de la session :

1. **Écriture concurrente sur le `lua_State`.** Les callbacks de
   `RegisterKeyBind` s'exécutent sur le thread d'event loop de UE4SS, pas sur
   le game thread. Corrigé en `-29` via `ExecuteInGameThread` — mais une
   corruption est survenue **après** ce correctif, donc soit il reste un
   écrivain concurrent non identifié, soit ce n'était pas la cause.
2. **Le volume brut d'appels.** Corrigé en `-31` : les callbacks d'axe
   appelaient `update_live_input()`, soit un `FText` + un `SetText` **par
   événement d'axe** — 119 406 appels mesurés en 11 minutes, environ
   175 écritures UMG par seconde, contournant entièrement le throttle du HUD.
   Ramené à 7,5/s.

**Comment trancher :** si les crashs cessent avec `-31`, c'était le volume. Si
leur fréquence est inchangée, la cause est ailleurs, et il faut désactiver les
familles de hooks une par une via `TAS_CONFIG` (`axis_hooks`, `key_hooks`,
`action_hooks`) jusqu'à isoler la coupable.

### Trois bugs qui étaient bien les nôtres

- **`pairs()` muté pendant l'itération.** Les callbacks de touches inséraient
  dans la table que le tick parcourait — insertion pendant traversée, rehash,
  itérateur invalidé, crash dans `luaH_next`. Corrigé par une file échangée :
  le tick remplace la table par une neuve avant de la lire.
- **`RootComponent` non validé.** Testé avec `if not root then` au lieu
  d'`is_alive`, alors que `root:K2_GetComponentLocation()` tournait dessus à
  chaque rafraîchissement.
- **Écriture Lua depuis le mauvais thread.** Les callbacks de `RegisterKeyBind`
  s'exécutent sur le thread d'event loop de UE4SS, pas sur le game thread où
  tourne le tick. Les deux écrivaient dans les mêmes tables : deux threads sur
  un seul `lua_State`, donc corruption. Symptôme : crash dans `getgeneric` ou
  `luaH_next` en spammant les touches, avec une adresse fautive contenant des
  octets ASCII (`0x687461BE`) — signature typique d'une table piétinée.
  Corrigé en reportant l'écriture via `ExecuteInGameThread`.

### Verdict sur les keybinds — `key_hooks` restera désactivé

C'est la conclusion la mieux étayée des deux sessions.

| Période | `key_hooks` | Crashs |
|---|---|---|
| 08/09 12:56 → 09/09 11:00 | off | **0** |
| 09/09, réactivés à 88 binds (au lieu de 629) | on | plusieurs |

Le nombre n'y change rien : c'est le mécanisme. Les callbacks de
`RegisterKeyBind` s'exécutent sur le thread d'event loop de UE4SS, et **toute
exécution Lua y alloue dans le tas partagé**.

Le correctif tenté le 08/09 — envelopper l'écriture dans
`ExecuteInGameThread(function() ... end)` — ne pouvait pas fonctionner :
**créer la closure est déjà une allocation Lua**, faite sur le mauvais thread
avant tout marshalling. On ne déplaçait que la seconde moitié du problème.

Signature constante : `getgeneric` / `luaH_next`, avec des adresses fautives
composées d'octets ASCII (`0x687461BE`, `0x67756266A5`) — un tas piétiné.

**Conséquence :** la ligne `E` n'affiche plus les touches. En échange, les
hooks d'**axe** tournent sur le game thread et sont sains (119 000 appels
mesurés sans incident), donc la ligne `I` reste vivante, et `S`/`G` donnent
sprint, accroupi et mode caméra via l'état du pawn. Remettre
`key_hooks = true` réintroduit les crashs en connaissance de cause.

### Sonder des noms ne doit jamais rester dans une boucle

Ma première version de la ligne `T` essayait quatre sources de temps à chaque
rafraîchissement. Les trois inexistantes levaient chacune une erreur Lua —
attrapée par `pcall` côté Lua, mais UE4SS plantait en générant la trace. Des
dizaines d'erreurs par seconde, deux crashs à la clé.

Les sondes F1 et F9 sont sûres **parce qu'elles sont déclenchées à la main**.
La même logique dans le tick est une machine à crasher. Une sonde doit
résoudre une fois, mémoriser, et abandonner définitivement en cas d'échec.

### Superposition d'overlays

Deux causes, toutes deux corrigées :

- `ClientRestart` se déclenche aussi quand le HUD **survit** (respawn,
  checkpoint) ; reconstruire dans ce cas empile un second panneau. `reset_overlay()`
  vérifie donc d'abord si l'overlay est encore vivant.
- Un hot-reload UE4SS repart d'un état Lua vierge alors que l'ancien panneau est
  toujours attaché au WidgetTree. `remove_stale_overlays()` détache les orphelins
  par leur nom avant d'en créer un nouveau.

### Configuration UE4SS

`EnableHotReloadSystem` a été passé à **0** dans `UE4SS-settings.ini`
(sauvegarde à côté). Le hot-reload est déclenché par **Ctrl+R** — une
combinaison qu'on tape naturellement en jouant — et il démonte puis remonte 629
keybinds et 12 hooks en pleine partie, ce qui gelait le jeu. On ne s'en sert pas,
`deploy.sh` demandant un redémarrage de toute façon.

## 6. Où en est le projet

Sur le pipeline de la section 9 du README :

```
UE4SS                          ✅
Découverte des objets Unreal   ✅
Identification du joueur       ✅  Shutter_PlayerController_C → .Pawn (Keith_BP_C)
Lecture de son état            ✅  position, rotation, vélocité, 4 enums ALS
Sauvegarde de l'état           ❌  ← prochaine étape
Restauration de l'état         ❌
Sauvegarde de l'état du jeu    ❌
TAS complet                    ❌
```

### Limite importante pour la suite

L'état est lu à **~7 Hz, pas à chaque frame**. Pour de l'affichage c'est sans
importance ; pour un TAS déterministe, c'est rédhibitoire — trois frames sur
quatre n'existent nulle part.

L'architecture correcte est de **découpler affichage et échantillonnage** : lire
l'état à chaque frame dans un buffer Lua (pur Lua, aucune traversée C++, c'est
ce qui coûte cher), et ne rafraîchir l'UMG que rarement. Ce buffer *est* la base
du système de snapshot.

Le frein : les lectures d'état sont des accès `UObject`, et passer de 7 à 60 Hz
multiplie par huit l'exposition aux signatures de crash listées plus haut. À
mesurer avant de s'engager.

### Ce qu'un snapshot devra contenir

Au-delà de position + rotation :

- les enums ALS (`MovementState`, `MovementAction`, `Stance`, `Gait`,
  `RotationMode`, `OverlayState`)
- vélocité, `Speed`, `MovementInputAmount`, `Acceleration`
- `InAirTimer`, `JumpCounter` pour les états aériens
- la rotation caméra (`GetControlRotation`) **et** celle de l'acteur

Restaurer l'une sans l'autre laisse la caméra désynchronisée.

## 7. Pièges à connaître avant de toucher au code

1. **Vérifier `BUILD = ...` dans la console** avant de conclure quoi que ce soit
   sur un comportement. Un fichier périmé côté jeu ressemble à un bug.
2. **Ne jamais appeler une `UFunction` sur un objet non validé** — `is_alive()`,
   pas `if not obj then`.
3. **Un callback de hook ou de keybind ne doit toucher ni l'UMG ni un UObject.**
   Il pose un drapeau, le tick fait le travail. Et un callback de **keybind**
   tourne sur un autre thread que le tick : toute écriture dans une table
   partagée doit passer par `ExecuteInGameThread`. Les callbacks d'**axe**
   tirent 60 fois par seconde et par axe : y écrire dans l'UMG contourne
   silencieusement tout throttle.
4. **Ne pas modifier une table pendant `pairs()`** — collecter puis supprimer.
5. **Déclarer en tête** toute fonction utilisée avant sa définition
   (`check_order.py` le vérifie).
6. **Un nom trouvé dans le pak n'est pas forcément un membre lisible** (cf.
   `ActualGait`). Vérifier en jeu : si la lecture rend un `TrivialObject`,
   la propriété n'existe pas — c'est une locale de fonction. Le test décisif
   est un témoin, un nom volontairement inexistant, qui rend la même chose.
7. **Les membres d'une `UserDefinedStruct` exigent le nom manglé**
   (`SlotUsed_16_<GUID>`), lisible dans le `.uasset` de la struct. Le nom
   propre rend `nil`.
8. `GetTimeSeconds()` est exposé comme `TrivialObjectValue` sur ce build de
   UE4SS — d'où la ligne `T` figée à zéro.
9. **La ligne `E` n'est pas un enregistrement d'inputs fiable** (pas de
   relâchement, pas de maintien). Pour un rejeu, se baser sur les événements
   d'axe et sur l'état du pawn.
10. **Un message d'erreur Lua impossible = tas corrompu, pas une erreur de
    logique.** Chercher qui écrit trop, ou depuis le mauvais thread.
11. **`update_hud()` et `tas_tick()` contiennent la même séquence d'appels.**
    `update_hud` ne tourne qu'à l'init. Ajouter un `update_X()` au mauvais
    endroit donne une ligne figée sur son texte initial, sans erreur — ça
    m'est arrivé trois fois (`update_input_text`, `update_camera_text`).
    Vérifier le numéro de ligne, ou factoriser les deux en une seule fonction.
12. **Lire le log avant de conclure.** Une ligne de HUD qui ne bouge pas est
    souvent une erreur Lua répétée, pas une donnée absente :
    `grep -E 'main\.lua:[0-9]+: [a-z]' UE4SS.log`.
